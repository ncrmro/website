A persona is a repo document that keeps a specific reader in the room. It tells humans and agents who the work is for, what that person needs, which trade-offs matter, and how technical the answer should be.

Persona reviews are the most common example. Pick a persona, then ask how the work reads from that point of view:

- How would my marketing site read to a _non-technical finance person_?
- How would these onboarding docs read to a _platform lead_?
- How would this pricing page read to a _budget owner_?
- How would this product demo read to a _sales representative_ preparing for an account call?

A defined persona gives each decision, design, and demo a specific reader. That usually makes the work faster because the trade-offs are less abstract.

A persona is not an Outfitter-only object. It is not a new resource type, a settings key, or a near-duplicate agent. The useful primitive is one Markdown file that says who the work is for.

```text
docs/personas/
  platform-lead.md          # Dana. Owns the pager. Distrusts new YAML.
  software-engineer.md      # Sam. Will paste your example straight into a terminal.
  marketing-manager.md      # Priya. Needs the claim to survive a landing page.
  sales-representative.md   # Marcus. Reads this out loud on customer calls.
```

That file can describe a role, biography, organization, constraints, vocabulary, and decision signals. The point is to replace "the user" with someone specific enough to make trade-offs.

This comes from the same place as Lean Startup personas: a product team needs to know who it is building for before it evaluates whether the thing works. Agents benefit from the file, but the file is for humans first. You should be able to read it in a planning meeting without caring which tool will consume it later.

Outfitter adds the runnable part. The pattern is small:

1. Keep one shared reviewer agent.
2. Commit one Markdown file per persona.
3. Append one persona file to the reviewer's system prompt at launch.
4. Ask the reviewer to inspect a design, code change, document, website, plan, or release.
5. Save the report with citations and provenance.

The reviewer owns the method. The persona file supplies the viewpoint. Swap the file and the method stays put — same agent, new hat, no second executable to maintain.

Step three is the one that matters. The persona is appended to the reviewer's system prompt, not typed at it: it becomes who the agent is for that session rather than a request the agent could weigh, set aside, or argue with. That is the difference between an agent reviewing as Dana and an agent reviewing a description of Dana.

The community profile has two persona skills: one to set up persona documents, and one to run reviews with them.

```text
/skill:persona-authoring Write a platform lead persona for this project.
/skill:persona-review Review the onboarding docs as the platform lead.
/skill:persona-review Open the new pricing page in the browser and review the design as the budget owner.
```

The first skill writes one portable Markdown persona file. The second skill uses that file with the shared `persona-reviewer` agent and owns the review method, evidence gathering, and report shape. The subject does not have to be text in the repo — point the reviewer at a running page and it reacts to the real design instead of a description of it.

<details>
<summary>Full Outfitter command</summary>

```bash
outfitter run persona-reviewer -- \
  --append-system-prompt docs/personas/platform-lead.md \
  --print "Review the onboarding docs from this persona's point of view."
```

</details>

A persona can be a role archetype, a named individual, or a composite grounded in customer research. It should not invent demographics, private facts, or fake validation. Persona feedback is a decision aid, not user research. It can show how a plausible platform lead might react to a setup flow. It cannot tell you what actual platform leads do in production.

That limit keeps the tool honest. It will not replace discovery; it stops you reviewing every change for an amorphous blob.

The same documentation change can produce different useful reports. Sam asks whether the example actually runs. Priya asks whether the benchmark number is safe to put in campaign copy. Marcus asks whether the paragraph survives being said to a customer without naming another account. Dana asks who gets paged when it breaks at 2am.

They deserve different reviews.

Once a persona file lives in the repo, it can steer more than review. It can shape specs, plans, docs, release notes, and design discussions. Outfitter makes the file runnable and its reports auditable, but its value starts before the run command.

[Spec Kit](https://github.com/github/spec-kit) is the clearest example. Every spec it writes opens with prioritized user stories, each one a journey in plain language with acceptance scenarios attached — straight from its [spec template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md):

```md
### User Story 1 - [Brief Title] (Priority: P1)

[Describe this user journey in plain language]

**Why this priority**: [Explain the value and why it has this priority level]

**Acceptance Scenarios**:

1. **Given** [initial state], **When** [action], **Then** [expected outcome]
```

The template says "user." The persona file says which one. Same slot, different feature.

Design with a specific person in mind. Then let the agent stop them from leaving.
